## OBJECTIVE
**User problem.** Changes has paths and staging buttons, but no durable per-file review checklist. A reviewer must repeatedly remember which files have already been read after reopening a panel or iterating with an agent. A whole-worktree revision is too broad: editing B must not reset reviewed A.

**Intended behavior.** A reviewer marks tracked file A as Viewed, then enables Unviewed to hide reviewed rows from the list. The full diff remains unchanged. Closing and reopening the same authorized worktree and comparison view restores A's marker if its exact change is unchanged. Editing A invalidates only A's marker; A returns to Unviewed with a textual reopen indicator.

**Measurable success.** In a synthetic eight-file comparison, marking three files shows `3 of 8 viewed`; Unviewed lists five rows. Editing one of those three yields `2 of 8 viewed` and six unviewed rows, without clearing the other two. Reloading preserves the two unchanged marks. The staged comparison, another worktree, checkpoint history, and GitHub reviews remain independent.

## REQUIREMENTS

### In scope (v1)
- R1 Tracked files in the live working-tree Changes surface only, in both staged and unstaged comparison modes. “Working-tree Changes” means `DiffBody`, not recorded/checkpoint/PR review surfaces. A path with changes in both modes has two independent identities and markers.
- R2 Persist local review markers by authorized worktree identity, staged/unstaged view, exact path, and opaque per-file exact-change fingerprint. Never use line counts, array position, branch name, thread ID alone, absolute path alone, or whole-tree `revision` as file identity.
- R3 Compute fingerprint and worktree identity under the existing guarded Git read. A missing, unstable, unsupported, or incomplete identity means no durable mark is offered for that row; explain why without disabling unrelated rows.
- R4 A checked Viewed control can be unchecked. Reopening a panel or application in the same local profile preserves valid marks. A changed fingerprint invalidates only that path/view. Never revive an older mark if contents later return to an older fingerprint after an observed invalidation.
- R5 Progress text and an Unviewed toggle affect the changed-file list only. Keep the complete selected-view diff, its content, scrolling, and accessible name intact. Counts use the complete current tracked comparison, not the filtered subset.
- R6 No review action changes Git, stages files, invokes an agent tool, or writes GitHub review state. Existing Stage/Unstage actions keep their existing server authority and revision checks.
- R7 Include keyboard/screen-reader support, focus recovery when filtered rows disappear, light/dark and narrow-panel styling, animation and reduced-motion behavior below.
- R8 Local-storage errors and stale asynchronous responses never silently erase saved markers, claim durable success, or apply state across owners. Provide inline recovery and a safe retry.

### Out of scope (v1)
- GitHub review writes or PR Viewed synchronization; GitHub reviews are a separate feature.
- Changes to staging behavior, commits, checkpoint state/history, recorded diffs, or inline comments ([#1288](https://github.com/skytuhua-org/Gen-V1/issues/1288)).
- Untracked files, per-hunk/line tracking, automatic scrolling/collapsing of the diff, mark-all, server synchronization, cross-device persistence, and agent-facing review tools.
- Durable review marks for conflicted entries, submodules, unsupported paths or types, or reads exceeding safety limits. Such tracked rows remain visible and unviewed with an explanation.

### Decisions (agreed) vs options
- Agreed: tracked-only; exact per-file identity under authorized Git read; independent staged/unstaged state; progress and Unviewed list filter; no durable mark without identity; full diff remains intact; final implementation task sends completed work to the front end team for review.
- Decided in this plan: use the existing client IndexedDB journal, not a new server table or bare localStorage map. Comparable per-project PR UI state already uses this journal; these are local review preferences, not durable Git mutations. Server supplies identity only. No workspace-action type or action-outcome receipt is needed.
- Decided: default filter is All on a fresh owner/mount. Filter preference is session-only, not a durable marker. Marks are shared by panels/windows in the same local profile and authorized worktree, not panel ID. Worktree replacement creates a new identity even at the same pathname.
- Decided: count all tracked paths changed in the selected comparison; identity-unavailable tracked rows count in the denominator but cannot count as viewed. Untracked rows retain existing presentation only in All, outside progress, labeled `Untracked · not included in viewed tracking`. Unviewed contains tracked rows only and states this in its accessible description.
- T01 discovery gates implementation details of bounded binary reads, attested legacy identity, and profile namespace. No unresolved choice changes the promised UX: if a safe implementation is unavailable, omit durable identity and show the unavailable state instead of guessing.

### UX flows
1. Open live Changes: load Git status and journal for its returned worktree owner; show progress after both settle. Initial load does not announce a burst of individual rows or animate them.
2. Mark a file: activate the native Viewed checkbox; save the captured fingerprint for that exact owner/view/path. Show `Saving…` until the journal transaction commits, then checked `Viewed`. Do not present a pending write as durable success.
3. Unviewed: activate the toolbar toggle. Hide only viewed tracked rows, preserve list order and the complete diff. Marking the focused last row moves focus to the next row's Viewed control, then previous, then the Unviewed toggle. Announce the new progress once.
4. Edit a viewed file: on Refresh or the next successful status load, compare current identities, clear only mismatches, show `Changed since viewed` on those paths, and include them in Unviewed. No new filesystem watcher is required in v1; until refreshed, say the checklist describes the loaded comparison.
5. Switch Staged: select the other side's list membership, counts, and marker map. A file with both index and working-copy edits may be viewed independently in each. Staging itself may move/change a comparison and invalidate only its affected identities on refresh.
6. Clean tree: show `0 of 0 viewed` and `No tracked changes in this view.` Empty filter result: `All tracked changes in this view are viewed.` plus `Show all` clearing the filter. Neither replaces the full diff.
7. Storage failure: keep the last acknowledged state, show `Viewed status could not be saved. Retry.` and leave the affected control unchecked (or checked for a failed uncheck). Retry revalidates the captured owner/fingerprint before saving. Read failure disables marking with `Retry viewed status`; do not initialize over unread data.

### Non-functional
- Preserve existing read authorization, path validation, resource limits and cancellation. No hooks, text conversion, external diff drivers, new network requests to GitHub, or direct filesystem reads from the browser.
- Store only version, opaque owner, paths, view, fingerprints and small reopen metadata; never file bytes, patch text, credentials or absolute host paths. Local journal remains profile-local; clearing profile data clears marks.
- One bounded status computation; do not spawn Git once per row. Batch per-view metadata and stream hashes where required. T01 benchmarks 1/100/1000 tracked changed files on the baseline and proposed implementation; target no more than twice baseline median refresh time on identical fixtures, record host/Git versions, and block rollout if exceeded without an accepted revised budget.
- Bound a worktree/view map to 1000 entries. If exceeded, disable new marks with explicit capacity text until absent entries are pruned; never silently evict visible valid marks. Prune only after a complete successful selected-view snapshot, never after errors or truncated data.

## DESIGN

### 1. Contracts (proposed additions, not existing interfaces)
Extend the existing `GitStatus`/`GitFile` definitions in `packages/workspace/tools.ts` and their readers together; do not move types as unrelated cleanup. Proposed wire shape:
```ts
// Additive fields; absent review data means viewed tracking is unavailable.
type FileReviewIdentity = { fingerprint: string } | { unavailable: string };
// GitStatus.review?: { version: 1; owner: string }
// GitFile.review?: { staged?: FileReviewIdentity; unstaged?: FileReviewIdentity }
```
- `owner` is a versioned opaque digest of server-authorized project and stable binding identity, including attested directory identity, not a client-supplied filesystem path. Managed: include binding ID and family identity. Legacy: include the enrolled original root identity, never the temporary snapshot. Hash canonical structured values with domain separation. If a stable authorized owner cannot be established, omit review data altogether.
- Fingerprints are versioned SHA-256 opaque strings. Hash canonical length-delimited tuples including comparison kind, exact path/oldPath when relevant, base and result modes, existence, and full base/result content digests. Do not hash aggregate revision, counts, localized display text or a binary placeholder.
- Unstaged is index → working bytes; staged is HEAD → index. For unstaged, do not include HEAD when it is not the base. An unrelated HEAD/branch change must not invalidate an unchanged index → worktree change. Base and result bytes include binary content; same-sized edits must differ. Include executable/symlink modes when supported; v1 symlink/submodule/conflict identities may be unavailable rather than insecurely followed.
- Stage an added file: HEAD side is explicit absent; deletion: result side absent; rename: include old and new paths plus both endpoints. Renaming does not migrate a mark by basename or content. Re-add at the same path after an observed disappearance starts unviewed.
- Per-view availability also establishes membership: parse nonblank corresponding porcelain side, excluding `?`, ignored and unmerged entries. Unmerged tracked rows remain visible as unavailable in both modes. Do not use `file.staged` as a proxy for “has no unstaged change.”
- Route remains the existing GET; no marker POST, action type, SQLite migration or new privilege. Old clients ignore additive fields; new clients receiving old responses disable Viewed with explanatory text, not a fabricated fallback fingerprint.

### 2. Backend (`packages/workspace/tools.ts`, guarded Git helper only if needed)
1. Carry attested logical owner information from `withGitOperation` into status while still inside the existing read boundary. Never re-resolve arbitrary paths after guard exit.
2. Obtain batched NUL-delimited HEAD/index metadata and exact endpoint digests with the admitted Git executable. Use explicit literal path handling for any path argument (`--` alone does not disable pathspec magic). Do not use shell interpolation, lossy path splitting, textconv or external drivers.
3. Read working files only via existing file custody primitives with no symlink traversal, bounded byte reads and before/after identity/content stability verification. Obtain repository blobs through a bounded binary-safe Git reader. `nativeGit` returns text, so T01 must prove byte preservation or add a narrowly scoped binary-capable guarded helper in `git-storage.ts`; do not hash UTF-8-decoded binary stdout.
4. Compute all endpoints and rendered diff from the same stable read. The project queue does not prevent an external editor changing files: compare relevant endpoint/index state before and after capture, retry once on detected drift, then return affected identities unavailable. Never attach a fingerprint for newer bytes to an older displayed patch. Guard custody loss still aborts the entire read under existing policy.
5. Keep existing `revision`, staging contracts, full diffs, stats and untracked handling unchanged. Per-file unsupported identity is recoverable; global Git/read authorization failures keep existing error behavior. A resource-limited/incomplete status must never prune saved markers or mint a partial durable identity.
6. Managed and legacy branches need separate tests. Legacy may offer markers only when the original-root owner and immutable projected bytes can be proven. Missing stable owner means tracking unavailable, not a fallback to project ID alone.

### 3. Local persistence and state transitions
Proposed new module `apps/web/src/changes-viewed-state.ts` owns a strict runtime schema, key construction, reconciliation and journal CAS retry. This is a planned path, not an existing module. Keep `journal.ts` unchanged unless T01 proves an essential integration gap.
- Key: `changes-viewed:v1:` plus canonical serialized `[profileHostNamespace, review.owner, view]`. T01 verifies the existing profile/host discriminator; if the origin already isolates both, record that evidence and use an origin-local constant. Never key on panel or thread alone.
- Value: `{version:1, entries:[{path,fingerprint,changedSinceViewed}]}` with bounded validated paths and no patch bytes. Each path stores only the latest acknowledged fingerprint or a reopen tombstone, not a history of all hashes. An unmark removes its valid marker; a mismatch replaces it with a tombstone so reverting bytes does not resurrect the old mark.
- Hydrate and validate before enabling controls. Reconcile only a complete successful current owner/view response: match → viewed; different → unviewed + reopen tombstone; absent from that view → remove entry; unavailable → display unviewed, disable marking and invalidate prior mark conservatively, without treating a failed global read as a clean snapshot.
- Track last successful snapshot per side; switching sides must not prune the side not being read. A mark click captures owner/view/path/fingerprint and request generation. Before committing, confirm they still match the loaded snapshot; on owner change, cancel pending UI effects and never write the replacement owner.
- Use `journalReadRecord`, subscribe, and `journalCompareAndSwap` to merge the latest map in one durable transaction. On CAS conflict reread/validate and reapply only the intended path change, bounded to three attempts; exhaustion offers Retry. Two windows marking different paths must preserve both; on the same path the last committed explicit action wins.
- Pending writes disable that row, not the whole panel. Hydration failure blocks writes, not full diff reading. Rejected schema versions show recovery error without overwriting saved data. Failed persistence is not reported as saved; retain last acknowledged rendered mark and retry the exact validated intent.
- No timer or watcher invalidates marks independently of a loaded comparison. Describe counts as the currently loaded review. On successful refresh invalidations apply immediately even if an agent run is active: these are local review notes, not Git writes.
- New profile starts empty; no migration of old state exists. A version bump isolates incompatible fingerprint semantics. Rollback ignores/removes the feature UI and leaves inert local records; it does not alter Git/checkpoints or require a database rollback.

### 4. Client (`apps/web/src/WorkspaceSurfaceBody.tsx`)
- Integrate owner-scoped state only inside `DiffBody`; reset request/hydration generations on owner and staged toggle changes. Keep `ChangesBody` checkpoint wiring and PR review state unchanged.
- Derive selected-view tracked membership first, calculate progress before filtering, then render All or Unviewed. Keep full selected-view `value.diff` / `value.stagedDiff` `<pre>` independent of checklist and filter.
- Existing Stage/Unstage remains a separate button, never nested in checkbox label. Its payload and `gitWrite===true` guard remain unchanged. On action completion refresh before reconciling identities.
- Counts are not shown as `0 of N` during journal loading: show `Loading viewed status…`; failure says `Viewed status unavailable`, with retry. Missing row identity shows unchecked disabled Viewed with linked reason.
- `Changed since viewed` is text, not just a dot. It remains for that path/view until explicitly marked again, manually unmarked from a valid state, or absent from a complete snapshot. Returning to a panel reads it from the local record.

Active background `var(--selection-bg)`, text `var(--text)`, border `var(--accent-fg)`; inactive inherits existing button styles. Wrap toolbar at narrow widths; no overlay or horizontal clipping.

Visible label `Viewed`; accessible label `Mark <full relative path> as viewed` / `Mark <path> as unviewed`. Path retains ellipsis visually with full path accessible; use `min-width:0` and wrapping secondary metadata. Stage button stays at the trailing edge.
- Unchecked: native empty box, normal path text. Checked: native check and `accent-color:var(--accent-fg)`, Viewed text unchanged; no strike-through, no row opacity that reduces contrast. ### 6. Security, compatibility and rollback
- Owner is derived from authorized binding, not trusted client data; fingerprints are read-only evidence, not write authorization or proof of human review. Preserve guarded read and existing staging action authority independently.
- Never follow symlinks to establish content identity, write blob objects to obtain hashes, or run user-configured clean/smudge filters. Unsupported types remain reviewable as text/list entries without durable marks.
- Additive optional response data permits mixed client/server versions. Stale owner responses and late journal completions cannot update a new panel owner. No GitHub API or telemetry receives local marks.
- Roll back additive UI/backend fields together; old journal records remain harmless. Revert the focused implementation PR through normal review, not destructive Git or profile cleanup.
