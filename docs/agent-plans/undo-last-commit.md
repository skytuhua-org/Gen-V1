## OBJECTIVE

If a user just committed with the wrong message or missed a file, they should be able to open the existing Commit form, review exactly which commit will be undone, and return to editing and staging without opening a terminal or losing file contents. One confirmed action moves the current branch back one commit, puts the former tip's changes back in the staged comparison, and restores its message as an editable draft. It never silently undoes a different tip.

**Implementation design proposed by this plan, not extra product scope:** disable detached HEAD rather than moving a detached checkout; fail closed when the host cannot classify tip eligibility or safely return its message. Do not treat a dirty worktree as ineligible by itself. If staged edits overlap the former tip, the existing index wins: a soft reset changes the comparison base, not the staged blob bytes. A user who proceeds with a current draft is explicitly told that this replaces that draft. Local-only means no containing locally known remote-tracking ref; local tracking data can be stale, so do not imply live remote verification.

## DESIGN

### Authority, state and data flow

1. Add a narrow optional `undoCommit` descriptor to the authorized Project Context read: either `{eligible:true, head, subject}` or `{eligible:false, reason}` (a finite enum, e.g. `running`, `remote-tracked`, `root`, `merge`, `detached`, `unavailable`). Absent means unsupported/legacy. Do not include the commit body in general context, URLs, telemetry, global feed or client journals. Only expose eligibility from the selected, authorized managed working copy and only use a descriptor matching the context's HEAD/revision. Mark the context response `Cache-Control: no-store` when shipping the preview. If eligibility cannot be read, keep the existing Commit/Changes reads working and disable Undo with an unavailable reason.
2. Under the existing guarded Git operation, determine the checked-out symbolic branch and its full tip OID. Check actual parent count with a local Git read; exactly one parent is required. Find remote-tracking branches that contain that OID (for example `git for-each-ref --contains=<expectedHead> --format=%(refname) refs/remotes/`, including packed refs; ignore symbolic aliases only if their destination has independently been checked). Never infer from ahead/behind counts, one upstream, or string equality against one remote tip. No fetch or remote writes. Read Git's subject and complete commit message from the same full OID, with explicit UTF-8/LF display handling and no lossy subject-as-body conversion. Reject malformed/unsupported or over-limit results before writing; never silently truncate the restored draft. An empty subject gets the literal UI fallback **(no subject)** and the short hash. An empty message stays empty; if an imported valid message exceeds the existing 4,000-character recommit limit but fits the safe read bound, restore it and require the user to shorten it before Commit.
3. Proposed wire request: one authenticated CSRF-protected `POST /api/projects/:projectId/actions` with the current owner thread and one operation ID; `type: 'undo-commit'`, strict `payload: {revision, expectedHead}`. No path, target ref, commit message, executable arguments, or credentials come from the browser. Branch is covered by the existing revision. Use the enum dispatch and existing intent/receipt lifecycle, not the legacy branch handler. Stage, unstage, commit and PR actions keep their current behavior.
4. Keep the final eligibility check in the same serialized, attested operation as the reset. Check concrete binding, owner run state, exact expected tip/revision, single parent and remote containment again; revision alone cannot catch a newly tracking remote ref. Probe Git metadata without broadening authority; if a state forbids soft reset (e.g. merge in progress, unmerged index), treat it as unavailable, not a partially supported merge flow. Capture the draft before any mutation and run only `git reset --soft HEAD~1` via guarded argv. Do not retry the command; the only intended mutations are Git's local tip/reflog/reset metadata, not the index/worktree, other branches or remotes.
5. Integrate the existing intent's start boundary at the first mutation for this new action: deterministic precondition rejection is not applied; once mutation may have started, retain uncertain-state semantics unless confirmed. At the final dispatch, recheck host run state and binding; use existing serialization/custody rather than a UI flag. The project queue alone does not prove thread-run admission is synchronized (see T01); if needed add the smallest owner-scoped admission fence and release on all outcomes. Do not hold a broad UI or global run lock. Never issue an automatic follow-up mutation when a response is lost.
6. Return an exact, typed confirmed result for Undo (proposed fields: `undoneHead`, parent/new `head`, `message`) only behind the existing same-owner receipt fence. Bind the returned OIDs to the intent and avoid storing a whole diff with the draft; keep necessary confirmation data within local owner-scoped receipt storage, not synchronization/feed output or error detail. Same-ID replay must return the existing result or stable uncertainty without resetting the parent. Keep older intent types readable. No new database migration; if rolling back, remove UI/dispatch while retaining historical receipt decoding as needed; rollback of code cannot undo a completed user's Git reset.

### Interaction and visuals

No front end design dependency: implement the interaction and motion specified here. The front end team's role is final review, not pre-implementation design.

- In Project tools → Commit, use the existing label/field and Commit button. Make the field a compact, full-width multiline textarea (initially two rows); preserve multiline bodies, existing required/length validity, the existing submit button/default semantics, and touch/focus styling. Lay out the original **Commit changes** and quiet secondary **Undo last commit** side by side with an 8px gap; wrap as a group onto the next line in narrow panels. Never hide the label or rely on an icon, color or hover. Display an adjoining explanation for disabled managed contexts, e.g. **Wait for the run to finish**, **This commit is on a remote-tracking branch**, **The first commit can't be undone**, **Merge commits can't be undone**, or **Refresh project details to check the last commit**. No Undo control in a read-only authority without supported managed Git; do not change what those surfaces can otherwise do.
- On activation capture the tuple of owner, current binding, HEAD, branch and revision, and the exact subject displayed for that tuple. Use the shared `Modal` primitive (`packages/ui-shell/Modal.tsx`) for an accessible dialog titled **Undo last commit?**. In a bordered inset show the subject as text with natural wrapping, and the short hash in muted monospace. Body: **This moves the current branch back one commit. Its changes will be staged and your files won't be discarded.** If the message field already contains a draft, also show **This replaces the current commit message draft.** Put **Cancel** and **Undo last commit** in the footer (Cancel first); focus Cancel initially, keep focus inside the modal, Escape cancels while idle, and return focus to the opener or the nearest surviving commit control on cancel. Use theme tokens for surface, border, foreground, muted text, focus ring and the confirm action; no custom overlay or red-only warning treatment.
- Use the shared modal entrance/exit when available; no competing backdrop animation. For the inset's entry, transition opacity from 0 and translateY from 4px over 150ms ease-out, then leave it still; remove motion for `prefers-reduced-motion: reduce`. Layout and focus do not wait for animation; no animated/strobing diff or list movement. Pending state keeps text/layout stable, shows **Undoing…** with `aria-busy` and disables resubmission, cancel and conflicting controls. Guard the modal's shared close callback during pending as well (it handles Escape, the header Close and backdrop). If run/owner/tip changes before dispatch, invalidate the confirmation with a visible reason; never silently switch the tip shown.
- On confirmed same-owner success, refresh context, keep Commit expanded, set the exact returned message in its field, focus it without scrolling the page, and announce **Commit undone. Changes are staged.** via a polite status. Offer the existing Changes navigation; refreshing/opening Changes → Staged must reflect the new HEAD and original index. Do not create a second commit or clear unrelated drafts. On cancel or rejection preserve the original draft. On known stale/ineligible results refresh and explain that the user must review again; on uncertain results say **Couldn't confirm the undo. Refresh and review Changes before trying again.** Do not populate the draft or claim success without a confirmed response. Re-enable Undo only after a fresh eligibility read and a new opt-in confirmation.
